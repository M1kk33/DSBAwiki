# Развёртывание и обслуживание DSBA Wiki

## Поддерживаемое размещение

Приложение предназначено для Cloudflare Workers через Sites. В `.openai/hosting.json` уже записан идентификатор созданного проекта и логические bindings `DB` (D1) и `BUCKET` (R2). Не создавайте новый Sites-проект при обычном обновлении этой wiki. Sites предоставляет реальные базы, хранилище, маршрутизацию и вход через ChatGPT.

1. Установите зависимости из lockfile: `npm ci`.
2. Проверьте типы и интеграционные сценарии локально согласно README.
3. Выполните `npm run build`. Выход: `dist/server/index.js`, `dist/client`, `dist/.openai/hosting.json` и копия миграций.
4. Установите секрет `ADMIN_BOOTSTRAP_KEY` в production-настройках Sites. Используйте случайное значение минимум 32 байта; не копируйте локальную тестовую базу на production.
5. Сохраните исходники в репозитории выбранного Sites-проекта, затем создайте версию именно этого коммита с архивом результатов сборки и опубликуйте её через Sites.
6. Дождитесь состояния `succeeded`, откройте сайт и `/api/catalog`, затем настройте администратора через `/admin`. Проверьте статус аудитории в Sites отдельно: private-размещение не делает сайт общедоступным.

Работающий локально dev-сервер и команда `npm start` сами по себе ничего не публикуют. Настройки доступа Sites и прикладная роль администратора — разные уровни: доступ к сайту не даёт право менять его содержимое.

Внешнее размещение без Sites потребует безопасного адаптера аутентификации вместо `app/chatgpt-auth.ts`, собственного процесса входа и проверки подписанной сессии на каждом запросе. Нельзя просто доверять входящим `oai-authenticated-user-*` на обычном Worker: за пределами Sites посетитель может подделать эти заголовки. Локальный mock-вход в production не включён.

## Изменения схемы

Правьте `db/schema.ts`, затем:

```sh
npm run db:generate
npm run setup:local
```

Просмотрите сгенерированный SQL до применения. Не переписывайте уже опубликованные файлы `drizzle/*.sql` и их метаданные. Добавляйте следующую миграцию. Локальный `setup:local` использует журнал Wrangler и не применяет старые миграции повторно; production-миграции применяет Sites перед загрузкой Worker.

Каталог — отдельный импорт данных приложения, а не SQL-миграция. Маркер `settings.catalog_imported` предотвращает повторное заполнение. Не удаляйте его, если не планируете повторный импорт.

## Резервные копии

Нужно сохранять **оба** хранилища: D1 хранит метаданные и ссылки на объекты; R2 — файлы. Git и архив сборки не являются резервными копиями контента.

Для локальной копии остановите dev-сервер и скопируйте всю `.wrangler/state` в отдельное защищённое место. Ключ активации и настройки `.env` храните отдельно; база содержит роль администратора, а не пароль.

Для production используйте экспорт D1 / механизм восстановления провайдера и резервную копию R2 средствами вашего аккаунта или администратора хостинга. Логические binding names из репозитория — не реальные production resource IDs. Получите реальные идентификаторы в настройках хостинга и не запускайте команды удалённого удаления или миграции с локальными placeholder IDs.

На время копирования обоих хранилищ приостановите загрузки, замены и другие записи. Иначе резервная БД может ссылаться на уже удалённую версию объекта R2. При пробном восстановлении проверьте наличие каждого объекта, указанного в `resources.file_key`.

План резервирования: перед миграциями и регулярно по мере наполнения; отдельно проверьте восстановление пары D1+R2 в тестовом окружении. При замене файла старый объект удаляется после успешной записи новой версии; восстановление старых байтов возможно только из резервной копии.

## Диагностика

- `503` в каталоге: проверьте binding DB, применённые миграции и серверный журнал.
- `403` при сохранении: проверьте вход, прикладную роль в `editors` и совпадение Origin с URL запроса. Обратный прокси должен сохранять корректный внешний origin.
- `409`: запись изменилась после открытия формы. Скопируйте свои правки, откройте редактор заново, затем примените их к актуальной версии.
- `413`: лимит файла 16 МиБ; общий запрос ограничен 17 МиБ. Загрузка идёт через PUT, чтобы multipart-запросы не проходили через отдельный парсер Server Actions во фреймворке.
- `404` у файла: материал скрыт/архивирован либо соответствующего объекта нет в R2. Администратор может проверить его через редактор.
- `orphan_file_cleanup` в журнале: не удалось удалить старый объект после успешного сохранения либо новый объект после ошибки записи. Сначала проверьте результат сохранения и актуальные `resources.file_key`; удаляйте только неподключённые объекты после резервного копирования.

Не публикуйте журналы с содержимым пользовательских документов, одноразовыми ключами, токенами или cookies. Встроенный API не возвращает технические стеки ошибок посетителям.

## Расширение

При потере доступа единственного администратора восстановление выполняет оператор хостинга: делает резервную копию и заменяет привязку в `editors` на проверенный `userId` нового аккаунта. Не используйте для этой операции произвольный идентификатор из клиентского запроса. Повторная установка bootstrap-ключа не назначает нового администратора, пока первоначальная настройка отмечена завершённой.

Для новых ролей расширяйте проверку `editors.role` и применяйте её сервером ко всем операциям. Для полноценного поиска PDF/Office добавьте отдельное ограниченное по ресурсам извлечение текста; не распаковывайте произвольные документы без лимитов в общем Worker. Для приёма материалов студентами понадобится отдельный поток отправки на модерацию; публичную запись прямо в библиотеку включать не следует.
